CURRENT IMPLEMENTATION NOTE (2026-08-29)
========================================

This file preserves the original product brief and is below implemented code, tests,
official current Microsoft documentation, and the shared implementation/guides in the
repository authority order. The current N:N Gateway intentionally refines the brief's
generic Entra data-plane wording:

- one Gateway brokers N external registrations;
- each registration binds its externalAgentId and unique Gateway-issued API key to
  one stored registration and one child Entra Agent ID under a selected reusable
  typed blueprint;
- the external client needs no Entra credential or managed-identity object ID for
  normal Gateway ingress; only a salted key hash is stored and the clear key is
  returned once;
- a lost one-time key response is replaced through the administrator credential
  lifecycle; it is never recovered from SQL/logs/idempotency or by repeating
  registration;
- one deterministic Gateway-worker FIC per reusable blueprint plus
  fmi_path=<child-agent-id> supplies outbound Agent 365 identity;
- the child receives only Agent365.Observability.OtelWrite, not the legacy Gateway
  ExternalAgent role;
- Agent 365 observability is the default, sanitized Azure Monitor export is optional,
  and Purview remains per agent;
- Entra child telemetry uses the child client ID as gen_ai.agent.id and the
  blueprint client ID as microsoft.a365.agent.blueprint.id; it omits
  gen_ai.agent.type and microsoft.a365.agent.platform.id;
- an Agent 365 OTLP HTTP 200 is endpoint acceptance, not proof that the event later
  landed in Defender CloudAppEvents.
- optional Prompt Shields and prompt-only Purview run through a pre-model Gateway
  endpoint; an allowed result issues a short-lived, single-use receipt required by
  protected completed interaction submission, while raw evaluation prompts are not
  stored in SQL or rendered in the Admin UI.

Scoped data-plane replay/conflict behavior is implemented by registration + endpoint
+ key with a canonical request hash and a SQL transaction-owned application lock held
through side effects and commit. Registration-bound fixed-minute rate limiting is
also implemented for credential, registration, and global scopes. Both SQL-backed
protections and their prepare scripts are deployed and verified in development, as
is the worker's session-owned per-job SQL application lock, but none has a real
multi-replica/failover production proof. The legacy global idempotency index remains
until a successful bounded canary.

Workflow v3 is deployed in development with explicit continuous registration,
automatic signed-in Administrator Registry completion, worker provisioning, and
data-plane relay. Staging and production retain exact-bound admission. The complete
release gate passes a zero-warning/error Release build and 1,121/1,121 tests (unit
409, Admin UI 151, end-to-end 106, security 111, runtime 144, integration 92,
architecture 108). PowerShell parsing passes 18/18; format, Bicep 23/23 templates and
5/5 parameters, OpenAPI YAML parsing, and diff checks also pass.

Both create-new and reuse-existing blueprint paths are Active and Available in
Microsoft 365 Admin Center. Bound Gateway activity/interaction requests returned
HTTP 202 and Agent 365 OTLP accepted sanitized exports. A reusable-blueprint Purview

Workflow v3 runs five worker stages to 71%, completes Registry through a signed-in

3. APPLICATION CONTEXT
==================================================

The gateway connects external AI agents to corresponding Microsoft Agent 365 agents.

Examples of external agents include agents built with custom frameworks or non-Microsoft platforms. The external agents do not include the Agent 365 SDK or CLI.

The gateway provides the Microsoft-facing integration on their behalf.

The intended logical relationship is:

External Agent 1 -> Gateway -> Agent 365 Agent 1
External Agent 2 -> Gateway -> Agent 365 Agent 2
External Agent N -> Gateway -> Agent 365 Agent N

Use a one-to-one mapping by default:

externalAgentId <-> agent365AgentId

Each external agent must have its own gateway registration and corresponding Agent 365 identity or instance when supported by official documentation.

The gateway is both:

1. A control plane for registration, provisioning, administration, and policy configuration.
2. A data plane for receiving activities, prompts, responses, and observability events.

Do not allow one external agent to submit data under another agent’s identity.

5. MICROSOFT ENTRA APPLICATION MODEL
==================================================

The gateway must be registered as a Microsoft Entra application.

Design separate trust boundaries where appropriate:

1. Gateway interactive web application registration
   - Authenticates administrators and operators.
   - Uses delegated access only where a signed-in administrator is required.

2. Gateway API application registration
   - Exposes gateway scopes and application roles.
   - Validates tokens issued to the management UI and agent clients.

3. Gateway workload identity
   - Used by backend workers and hosted components.
   - Prefer managed identity or workload identity federation where supported.

4. External-agent client registrations or workload identities
   - Each external agent must authenticate independently.
   - Each identity must be bound to only the corresponding externalAgentId.
   - Do not trust an externalAgentId supplied in a request without comparing it to authenticated identity claims.

The gateway must receive all documented permissions required to provide enabled functionality, but no more.

Do not interpret “all permissions” as unrestricted Microsoft Graph, tenant-wide, or Global Administrator access.

Apply:

- Least privilege
- Separation of duties
- Administrative consent only when required
- Managed identity where supported
- Certificate credentials over client secrets for production, where managed identity is unavailable
- Azure Key Vault for credential material
- Credential rotation
- Conditional Access considerations
- Privileged Identity Management considerations
- No secrets in source code, configuration files, logs, API responses, or database columns

Produce an exact permissions matrix. Never guess permission names.

For each permission, include:

- API resource
- Exact permission name
- Delegated or application
- Admin consent requirement
- Feature requiring it
- Official documentation URL
- Least-privilege justification
- Whether it is required at runtime or only during provisioning

9. PROVISIONING WORKFLOW
==================================================

When an administrator registers an external agent:

1. Validate uniqueness and authorization.
2. Create a Draft AgentRegistration.
3. Create a ProvisioningJob.
4. Write an outbox message in the same database transaction.
5. Return HTTP 202 Accepted with the agent and operation URLs.
6. Let the provisioning worker execute the documented Agent 365 provisioning workflow.
7. Provision or associate the blueprint.
8. Provision the corresponding Agent 365 agent or instance.
9. Configure documented permissions.
10. Configure managerApplications if required by Agent 365 documentation.
11. Record only safe identifiers in Azure SQL.
12. Place credential material in Key Vault if credential material must be stored.
13. Mark the registration Active only after all required steps succeed.
14. Record an audit event.
15. Return a stable error code and safe error summary if provisioning fails.

The process must be:

- Asynchronous
- Idempotent
- Retryable
- Auditable
- Resumable
- Safe against duplicate agent creation

Define a provisioning state machine.

Include compensation behavior, but do not automatically delete successfully created Microsoft resources if deletion could cause data loss or require separate authorization. Mark such cases as RequiresManualIntervention.

Provide a reconciliation job that detects:

- Missing Agent 365 resources
- Unexpectedly deleted resources
- Configuration drift
- Permission drift where documented APIs permit checking it
- Gateway registrations stuck in transitional states

12. PURVIEW PROCESSING
==================================================

Purview is configured per agent:

purviewEnabled = true or false

When enabled:

1. Determine the applicable Purview protection scope using the officially documented process.
2. Evaluate prompts, responses, and supported file content using documented Purview APIs.
3. Enforce documented policy actions.
4. Send supported interaction records into Purview.
5. Record only the minimum gateway-side decision metadata.
6. Avoid duplicating full prompt and response content in gateway logs.
7. Respect tenant retention and privacy requirements.

Supported modes:

AuditOnly
- Send or record the interaction using documented Purview capabilities.
- Do not block the external agent unless required by Microsoft policy semantics.

Enforce
- Evaluate before release of content when official APIs support inline enforcement.
- Return Allow, Block, or another exact documented policy action.
- Do not reduce a richer Microsoft policy result to Allow or Block without explaining the mapping.

When Purview is disabled:

- Do not call Purview APIs for future interactions.
- Continue minimum security and operational logging.
- Do not claim that disabling Purview removes historical Purview records.
- Record the configuration change in the gateway audit log.

Clearly separate:

- Policy evaluation
- Interaction submission
- Audit visibility
- Gateway observability
- Purview reporting

Do not build an API that attempts to retrieve Purview analytics unless official documentation provides such an API.

- Outbox pattern

Define fail-open versus fail-closed behavior.
